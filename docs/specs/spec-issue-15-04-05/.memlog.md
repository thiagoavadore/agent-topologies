- (decision) 04 starts from 03's mandated rung: the timeout in `charge()`/`send_email()` must be `http_timeout("<service>")`, workers cannot write overrides, only the platform lead grants them. Reason: 03 measured that with a local route open nobody touches the hub (0 of 10 contested), so the hub must be the only seam for the management layers to matter. Disclosed as a design choice.
- (decision) 04 workers are one per service (8, Sonnet 5.5), identical prompts in every arm, and run once per run index; all four arms resolve the same worker replies (paired design). Reason: worker prompts do not depend on the arm, so reusing one draw removes worker noise from the comparison and cuts 24 worker calls per index. Disclosed.
- (decision) 04 arms: `flat` (platform lead over 8 workers, sees every service's needs), `by-team` (3 sub-leads, no owner team split, groups follow the booking call graph), `by-runtime` (3 sub-leads by language, splits Team Rentals and Team Fleet and both of bookings-api's call edges), `by-runtime-registry` (same sub-lead replies as by-runtime, plus a harness-attached needs registry at the platform lead). Group sizes 3/2/3 in both cuts. Reason: same shape, only membership differs; the registry arm asks whether a published Team API substitutes for an aligned cut.
- (decision) 04 information rule, same in every arm: a lead sees the `service.yaml` (with `needs`) of the services it manages directly. The flat lead manages all eight; a sub-lead its group; the tiered platform lead manages sub-leads, so it sees only their requests (plus the registry in that arm). Reason: this is what a middle layer is for (span of control), and it is where information compresses.
- (decision) 04 upward protocol: requests only (hub key, value, one-line reason), no free-text note, no structured override request. Same as 03's worker hub_changes. Reason: continuity with 03 and no prompt invitation to list standing constraints, which would hand the platform lead the needs list in every arm and make the cut irrelevant by construction. This is the choice that creates the "silent dependent" effect; disclosed, and tested directly by the registry arm.
- (decision) 04 models: workers Sonnet 5.5; sub-leads and platform lead Opus 5.5 (leads, as in 03's reducer). No merge report call (no partial failure in 04).
- (decision) 04 score: checker only for fixed/regressed. Folder-local deterministic metrics: per-request harm (would this hub value, applied with no override, break a regression need?), inside/outside the requester's subtree, escalations, and a coupling ladder per regression need: not-threatened, absorbed-at-sub-lead, caught-at-top, reached-hub, introduced-by-top.
- (decision) 04 has no failure injection. Reason: 03 already measured partial failure; keeping 04 to one variable (the cut) keeps it buildable by Monday.
- (decision) 05 is service-local: consumers may write overrides and code literals (contract allows), `platform.yaml` is not in any consumer's path list. Reason: hold 03's hub question fixed so only the channel varies; 03's overrides-allowed rung fixed about 9 of 11 with zero regressions, so clean-message fix rates should be high and losses attributable to the channel.
- (decision) 05 producer is a deterministic scanner publishing one `risk.reported` per catalogue risk (11), shuffled per run. Reason: the question is delivery and ownership, not detection; 02 already measured detection. Disclosed as a stand-in.
- (decision) 05 consumers: one Sonnet 5.5 agent per owner team (6), one call per delivered message, sequential per team, told to fix only the reported risk. Subscriptions from pristine owner fields; fleet-telemetry has no subscriber. Reason: per-message processing makes redelivery, duplicates and wrong routing real; the routing hole is born from the fixture's own unowned service, not injected.
- (decision) 05 arms: `no-owner` (plain Publish-Subscribe Channel, at-most-once, no schema, no store), `steward-agent` (same mechanics, plus an Opus steward that reads the whole Message Store once after pass 1 and issues corrective actions), `platform-owned` (code guarantees: Datatype Channel schema with Invalid Message Channel, acks with one redelivery, Idempotent Receiver, Dead Letter Channel, Correlation Identifier plus Message History; an Opus platform agent reads only the two exception channels once and issues the same action set). Reason: the three answers to "who looks after the channel": nobody, an agent babysitter, the platform as a product.
- (decision) 05 action set shared by steward and platform agent: redeliver, route (with corrected service), assign_owner, return_to_producer; one round. Reason: equal powers, different view and different guarantees underneath; one round bounds cost.
- (decision) 05 faults, injected by the harness, identical per run index across arms: malformed (category, file, locator removed), wrong-service (service moved to the next service of another team, file kept, 02 style), consumer-crash (first delivery fails, no model call), duplicate (delivered twice). Four per run on four distinct routable risks by a fixed rotation; each kind hits all nine routable risks over nine runs. Plus the natural unroutable fleet-telemetry messages every run.
- (decision) 05 has no separate `dropped` kind. Reason: a transit drop and a consumer crash both mean "taken off the channel, never processed"; on an owned channel both are recovered by the same ack and redelivery code, so a second kind would add a by-construction row and no new information. Consumer-crash is the realistic path. Said in the README.
- (decision) 05 traceability is scored with a same-model investigator (Opus 5.5, identical prompt in every arm) given the records each arm actually keeps: team local logs (no-owner), the steward's Message Store (steward-agent), the platform's store with Dead Letter and Invalid Message channels (platform-owned). Its per-risk cause enum is scored against harness ground truth. Reason: tracing ability must be model-measured from evidence, not credited by construction to the arm that keeps a log.
- (decision) 05 paired ablation of trace context: in platform-owned runs a second investigator call gets the same records with Correlation Identifiers and Message History stripped and copies re-labelled. Reason: isolates what trace context buys (the four-rights "platform enforces trace context") at one extra Opus call, no extra consumer calls. First item to cut if late.
